# 시작 가이드

이 사이트는 **프로젝트를 구현하기 전에 정해야 할 것들**을 모아둔 문서 모음입니다.
코드가 아니라 **합의**를 저장하는 곳입니다.

처음이라면 이 페이지만 읽고 따라 하시면 됩니다.

## 전체 흐름

```
[1] 인터뷰    흩어진 생각·문제   →  기획안 1개
[2] 구조화    기획안             →  프로젝트 설계도
[3] 디자인    설계도의 디자인 항목  →  디자인 규칙 + 시안
[4] 구현      설계도 + 시안        →  코드

 └ 선택  ERD    스키마 자료 → DBML + 시각 ERD HTML      (erd-visual)
```

앞 단계의 산출물이 다음 단계의 입력이 됩니다. 건너뛰면 뒤에서 되돌아옵니다.
**선택 항목은 흐름을 막지 않습니다.** 필요한 프로젝트에서만 씁니다.

**2단계의 산출물을 "문서"라고만 보면 과소평가입니다.** 만들기 전에 정해야 할 것들을
빠짐없이 꺼내 놓고, **정해진 것과 아직 아닌 것을 갈라놓은 상태** — 그게 설계도입니다.

## [1] 인터뷰 — 기획안 만들기

**언제 쓰나요.** 머릿속에 문제나 아이디어만 있고 정리된 문서가 없을 때.
이미 기획안 파일이 있다면 1단계를 건너뛰고 2단계로 가도 됩니다.

**어떻게 실행하나요.**

```
/project-interview
```

**무엇을 하나요.** 선택형 질문으로 인터뷰합니다. 모든 문항에 "아직 모름"이 있어서
모르는 것은 모른다고 답하면 됩니다. 억지로 채우지 않습니다.

| | 묻는 것 |
| --- | --- |
| 정체 | 클라이언트·회사·프로젝트명, 업종 |
| **문제** | 증상 → 근본 원인 → 비용 → 지금은 어떻게 버티는지 |
| 대상 | 실제 쓰는 사람과 결정하는 사람 (다를 수 있습니다) |
| **성공** | 3개월 뒤 무엇이 달라져야 하는지, 어떻게 확인하는지 |
| **범위** | 꼭 필요한 것 3가지 / **하지 않을 것** |
| 제약 | 일정과 그 날짜인 이유, 예산, 연동, 규제 |
| 자산 | 로고·콘텐츠·도메인·실적이 있는지 |
| 참고 | 좋게 본 서비스 **그리고 싫은 서비스** |

**무엇이 나오나요.** 파일 3개.

| 파일 | 내용 |
| --- | --- |
| `Docs/_intake/…md` | 기획안 |
| `Docs/_discovery/decisions.md` | 인터뷰에서 정한 것 (`DI-001`) |
| `Docs/_discovery/open-questions.md` | 답을 못 받은 것 (`OQ-01`) |

**알아두면 좋은 것**

- "○○를 만들어줘"로 시작하면 **한 번 되돌립니다.** 무엇을 만들지보다 무엇이 문제인지가 먼저입니다.
- **"하지 않을 것"을 반드시 묻습니다.** 이게 비어 있으면 나중에 범위 분쟁이 납니다.
- 모른다고 답한 것은 **대신 정하지 않습니다.** 그대로 2단계로 넘어가 리스크가 됩니다.

## [2] 구조화 — 프로젝트 설계도 만들기

**무엇을 하는 단계인가요.** 웹사이트 문서를 만드는 단계가 **아닙니다.**
무엇을 만들든, 그것을 만들기 **전에 정해야 하는 것들**을 빠짐없이 꺼내
정해진 것과 아직 아닌 것으로 갈라놓는 단계입니다.

**언제 쓰나요.** 기획안이 준비됐을 때. 1단계 산출물이든 직접 쓴 문서든 상관없습니다.

**어떻게 실행하나요.**

```
/project-init ingest     기획안을 읽어 문서를 채웁니다
/project-init check      규칙 위반을 검사합니다
/project-init build      이 사이트를 다시 만듭니다
```

기획안 파일을 직접 갖고 있다면 `Docs/_intake/` 에 넣고 `ingest` 하면 됩니다.

**무엇을 하나요.** 기획안을 읽어 **정해진 것과 안 정해진 것을 분리**하고, 단계별 문서로 펼칩니다.
착수 전에 두 가지를 물어봅니다.

| | 묻는 것 |
| --- | --- |
| 범위 옵션 | 검색 노출 · AI 노출 · 측정 · 접근성 · 다국어 등 13개를 켤지 끌지 |
| 스택 | 기획안에 기술이 언급됐다면 버전까지 (조회한 실제 최신 버전으로) |

끈 항목의 섹션은 만들어지지 않고, 전부 끈 문서는 아예 생기지 않습니다.
선택 결과는 홈의 **범위** 패널에서 볼 수 있습니다.

**무엇이 나오나요.** 왼쪽 메뉴의 문서 전부와 이 사이트(`Docs/index.html`).

### 무엇을 만들든 적용됩니다

문서 구성은 **모듈 조합**으로 정해집니다. 프로젝트 성격에 따라 필요한 묶음만 붙습니다.

| 만들려는 것 | 붙는 모듈 |
| --- | --- |
| 기업 웹사이트 | 브랜드 · 대상 · 화면 · 디자인 · 접근성 · **IA/콘텐츠/검색 노출** |
| 모바일 앱 | 대상 · 화면 · 디자인 · 접근성 · **권한/스토어** · 백엔드 |
| 사내 시스템 | **업무 프로세스(As-Is/To-Be) · 권한 · 데이터 이관 · 교육** · 백엔드 |
| AI 제품 | **모델 · 프롬프트 · 평가셋 · 실패 모드 · 비용/지연** |
| 데이터 파이프라인 · 백엔드 전용 | 백엔드 · 엔지니어링 · 딜리버리 (화면 관련 모듈 없음) |

미리 만들어진 조합(프리셋)이 없는 유형은 **모듈을 직접 골라** 쓰면 됩니다.
화면이 아예 없는 작업, 하드웨어·업무 자동화 같은 것도 같은 절차로 다룹니다.

`core`(브리프 · 리스크 · 의사결정 · 용어)는 무엇을 만들든 항상 붙습니다.
어떤 프로젝트든 **"왜 만드는가 / 무엇이 안 정해졌는가 / 무엇을 언제 정했는가"** 는
공통이기 때문입니다.

### 산출물은 두 층입니다

| | |
| --- | --- |
| `Docs/*.md` | **원본.** 합의 그 자체이고 git으로 이력이 남습니다 |
| `Docs/index.html` | **읽는 방법.** `.md`에서 매번 다시 만들어지는 생성물입니다 |

이 사이트는 결과물이 아니라 **창**입니다. 내용을 바꾸려면 `.md`를 고치고 다시 빌드하세요.

### 이 설계도가 쓰이는 곳

3·4단계 입력만이 아닙니다.

- **견적·계약** — "하지 않을 것"과 수용 기준이 범위 분쟁을 막습니다
- **팀 합류** — 새로 온 사람이 배경과 결정 이력을 한 번에 읽습니다
- **인수인계** — 왜 그렇게 정했는지가 의사결정 기록에 남아 있습니다
- **되돌아보기** — 6개월 뒤 "이거 왜 이렇게 했지"에 답할 수 있습니다

**알아두면 좋은 것**

- **규칙을 어기면 사이트가 만들어지지 않습니다.** 프론트매터 누락, 필수 섹션 없음,
  깨진 문서 링크, 정의되지 않은 추적 ID가 있으면 빌드가 멈춥니다.
  귀찮아 보이지만 이게 문서가 흐트러지지 않는 유일한 이유입니다.
- **확인되지 않은 사실은 채우지 않습니다.** 매출·고객사·수치는 확인된 것만 씁니다.
  없으면 `TODO(주체)` 로 남아 홈에 집계됩니다.
- `Docs/index.html` 을 직접 고치지 마세요. 다음 빌드에 덮어써집니다.
  내용을 바꾸려면 `.md` 파일을 고치고 다시 `build` 하세요.

### 코드 변경 후 문서 갱신하기

React·Node 코드가 바뀌면 먼저 변경 성격에 맞는 `Docs/*.md` 원본을 수정합니다.

문서 번호는 모듈 조합마다 달라지므로 **파일명 뒤쪽(이름)으로 찾습니다.**

| 코드 변경 | 주로 갱신할 문서 |
| --- | --- |
| 화면·상태·폼 | `*-screen-spec.md`, 필요 시 `_design/` |
| DB 모델 | `*-data-model.md` |
| API · 외부 시스템 연동 | `*-api-spec.md` |
| 인증·권한·감사 | `*-role-permission.md`, `*-security-audit.md` |
| 테스트·배포 | `*-qa-test-plan.md`, `*-release-ops.md` |
| 코드 규칙·완료 조건 | `*-dev-standard.md` |
| 진행도 | `*-wbs-schedule.md` — 과업 진척과 지연 |
| 범위가 바뀌었을 때 | `*-deliverable-register.md` **버전 이력에 추가** + `*-requirements.md` |
| 리스크·결정 | `*-risk-open-questions.md`, `*-decision-log.md` |

> **범위가 바뀌면 산출물 정의서를 먼저 고칩니다.** 정의서가 메뉴와 WBS 의 원천이므로,
> 여기를 건너뛰고 개별 문서만 고치면 근거 없는 산출물이 남습니다.

수정한 문서는 프론트매터의 `updated`와 하단 변경 이력을 오늘 날짜로 갱신합니다.
그 다음 **`Docs/`가 보이는 프로젝트 루트**에서 아래 명령을 순서대로 실행합니다.

```bash
node ~/.codex/skills/project-init/build.mjs check --docs=Docs
node ~/.codex/skills/project-init/build.mjs build --docs=Docs
```

- `check`가 실패하면 출력된 파일·항목을 고친 뒤 다시 실행합니다.
- `check`가 통과해야 `build`로 `Docs/index.html`을 최신화합니다.
- Claude 원본 경로를 직접 쓸 때는 `~/.claude/skills/project-init/build.mjs`도 같습니다.
- 다른 위치에서 실행한다면 `--docs`에 실제 경로를 지정합니다.

AI에게 맡길 때는 다음처럼 요청할 수 있습니다.

```text
이번 React·Node 코드 변경을 분석해서 관련 Docs/*.md의 updated와 변경 이력을 갱신하고,
project-init check를 통과시킨 뒤 build하여 Docs/index.html까지 최신화해줘.
확인되지 않은 배포·실장비 상태는 완료로 표시하지 마.
```

장비 관련 변경은 통합 문서와 함께
`_archive/장비관련/html/07_프론트화면_데이터가이드.html`도 갱신합니다.

### 문서를 읽는 법

| 메뉴 | 쓰임 |
| --- | --- |
| **홈** | 진행 상태, 해결해야 할 Blocker, 대기 중인 자료, 범위 |
| **추적성 매트릭스** | 요구사항·리스크·결정이 어디서 정의되고 어디서 참조되는지 |
| **1단계 · 기획** | 인터뷰 기록 (있을 때만 표시) |
| **3단계 · 디자인** | 디자인 규칙 · 수정 이력 · 시안 목록 (있을 때만 표시) |
| 단계별 문서 | 전략 → 기획 → 디자인 → 엔지니어링 → 딜리버리 → 관리 |

문서 상태는 `초안` → `검토중` → `확정` 순으로 올라갑니다.

## [3] 디자인 — 규칙과 시안 만들기

**언제 쓰나요.** 설계도가 어느 정도 채워졌을 때. 무엇을 만들지 정해져야 어떻게 보일지를 정할 수 있습니다.

**어떻게 실행하나요.**

```
/project-design
```

**무엇을 하나요.** 먼저 **어떤 근거로 디자인할지** 물어봅니다. 셋 중 하나를 고르시면 됩니다.

| 방식 | 이럴 때 | 무슨 일이 일어나나요 |
| --- | --- | --- |
| **벤치마킹 URL** | 참고할 실제 사이트가 있을 때 | 그 페이지를 열어 색·타이포·여백·레이아웃을 뜯어보고 규칙으로 바꿉니다 |
| **참조 이미지** | 시안·스크린샷·무드보드가 있을 때 | `Docs/_design/images/` 폴더를 만들어 드립니다. 이미지를 넣고 **다시 부르시면** 전부 읽어 분석합니다 |
| **텍스트 설명** | 말로만 있을 때 | 되물어 구체화합니다. "깔끔하게"는 여백인지 색인지 요소 수인지 되묻습니다 |
| **Figma 파일** | 디자이너 파일이 있을 때 | 변수·컴포넌트를 **정확한 값으로** 읽습니다. URL·이미지는 추정이 섞이지만 이건 원본입니다 |

섞어서 쓸 수도 있습니다. 그때는 **서로 충돌하는 지점을 짚어 드립니다.**

**무엇이 나오나요.**

| 위치 | 내용 |
| --- | --- |
| `Docs/_design/styleguide.html` | **스타일 가이드** — 색 견본·명도비·타이포·상태를 실제로 렌더 |
| `Docs/_design/tokens.css` | 토큰 단일 출처. 여기만 고치면 시안 전체가 따라옵니다 |
| `Docs/_design/design-rules.md` | 디자인 규칙 — 토큰 값과 **그 근거** |
| `Docs/_design/change-log.md` | 스타일 수정 이력 (`DS-001` 형식) |
| `Docs/_design/mockups/*.html` | 화면 시안 — 이 사이트에서 새 탭으로 열립니다 |

빌드하면 왼쪽에 **`3단계 · 디자인`** 메뉴가 생기고 홈에 시안 목록이 붙습니다.

**알아두면 좋은 것**

- **Blocker가 열려 있으면 먼저 알려 드립니다.** 로고나 회사 표기가 미정인 채로
  시안을 만들면 그 시안은 다시 만들게 됩니다.
- **확인한 값과 추정한 값을 구분해 적습니다.** 화면을 직접 못 보고 유추한 색은
  `추정`으로 표시합니다. 보지 않은 값을 확정처럼 쓰지 않습니다.
- **벤치마킹은 복제가 아닙니다.** 가져올 것과 가져오지 않을 것을 나눠 적고,
  로고·사진·일러스트는 가져오지 않습니다.
- **처음에는 화면 1~3개만** 만듭니다. 전부 만들고 방향이 틀리면 전부 버리게 됩니다.
- **스타일을 고칠 때마다 이력이 남습니다.** "좀 더 밝게" 같은 요청이어도 결과 값과
  이전 값을 함께 적어서, 나중에 왜 이 색이 됐는지 되짚고 되돌릴 수 있습니다.
- 2단계 디자인 시스템의 토큰과 충돌하면 **말없이 덮어쓰지 않고** 차이를 보여드립니다.
- **글로만 남기지 않습니다.** `#12447E` 가 어떤 파랑인지는 봐야 압니다.
  스타일 가이드가 토큰을 실제로 렌더하고 **명도비를 계산해** AA 통과 여부까지 표시합니다.
  문서 안의 색상 값에도 견본 칩이 자동으로 붙습니다.

## [4] 구현 — 개발

```bash
/project-build
```

설계도와 시안을 **돌아가는 코드**로 바꿉니다.

**입력** — `기술 아키텍처`(스택·폴더 구조·렌더링), `요구사항 정의서`(수용 기준 `R-xx`),
`IA`(사이트맵·라우트), `화면 설계서`(섹션·폼·상태), `개발 표준`(완료의 정의),
`QA`(릴리즈 체크리스트),
그리고 3단계의 `tokens.css` · `design-rules.md` · 시안.

**산출물**

```
src/  scripts/
Docs/_build/
├── build-rules.md    구현 규칙 (id: build-rules)
├── change-log.md     구현 이력 (BD-001 형식)
├── parity.html       **시안 ↔ 구현 대조기**
└── coverage.md       화면 정의서 대비 커버리지
```

**이 단계의 성질**

- **스택을 고르지 않습니다.** 기술 아키텍처 문서에서 읽습니다. 문서에 없는 의존성을
  추가하려면 이유를 적고 알립니다
- **토큰을 복사하지 않습니다.** `tokens.css` 를 링크합니다. 값을 옮겨 적으면 두 곳이 되고,
  두 곳은 반드시 갈라집니다. 검증기가 복사를 감지합니다
- **대조기를 먼저 놓습니다.** 시안을 코드로 옮기면 클래스 이름이 달라져 눈으로 대조할 수
  없게 됩니다. `data-parity="이름"` 표식으로 짝을 맞춰 색·타이포·형태·너비를 비교합니다
- **3단계 `audit.html` 을 그대로 씁니다.** 시안을 통과시킨 기준을 구현도 통과해야 합니다.
  대상 URL 만 개발 서버로 바꿉니다
- **완료는 요구사항 정의서가 판정합니다.** 느낌이 아니라 수용 기준입니다. 진행률의 절반이
  `R-xx` 통과 비율이고, 마지막 10%는 **사용자 최종 승인**입니다

**시안이 없는 화면**은 4단계가 `design-rules.md` 와 `tokens.css` 를 근거로 채웁니다.
3단계는 방향 확인을 위해 1~3개만 만들기 때문입니다. 무엇을 채웠고 무엇이 남았는지는
`coverage.md` 에서만 보면 됩니다.

## [선택] ERD — 데이터 구조를 그림으로

> **`erd-visual` 스킬이 준비되어 있습니다.** 필수 단계가 아니라 **옵션**입니다.
> DB나 정해진 데이터 구조가 있는 프로젝트에서만 쓰면 됩니다.

**언제 쓰나** — 이럴 때 켜세요.

- 기존 시스템의 스키마를 받아서 구조를 파악해야 할 때
- 고객·팀에게 **테이블 관계를 그림 한 장으로** 설명해야 할 때
- 데이터 모델 문서(`*-data-model`)를 그림으로 뒷받침하고 싶을 때

**무엇을 넣나** — 스키마 정보가 담긴 파일이면 됩니다.

| 형식 | 관계 근거 |
| --- | --- |
| DDL SQL (`CREATE TABLE`) | `FOREIGN KEY` 제약 — **사실** |
| Excel · CSV (메타데이터 내보내기) | 자료에 따라 다름 |
| XML (메타데이터) | 자료에 따라 다름 |
| Prisma · JSON Schema | relation 선언 · `$ref` |

**무엇이 나오나**

```
ERD/
├── schema.dbml   dbdiagram.io 에 그대로 붙여넣을 수 있습니다
├── erd.html      고객에게 보낼 파일. 서버 없이 열립니다
├── erd.svg       Figma 로 끌어다 놓으면 벡터로 풀립니다
└── report.md     무엇을 근거로 했는지 · 무엇이 추정인지
```

**`erd.html` 은 그림이 박힌 파일이 아닙니다.** 안에 엔진이 들어 있어서
**DBML 을 고치면 그 자리에서 다시 배선**됩니다. 받는 쪽은 아무것도 설치할 필요가 없습니다.

**쓰는 법**

```bash
node ~/.claude/skills/erd-visual/build.mjs build --dbml=ERD/schema.dbml
node ~/.claude/skills/erd-visual/build.mjs check --dbml=ERD/schema.dbml
```

또는 `/erd-visual` 로 스킬을 부르고 자료 위치를 알려주세요.

> **이 스킬의 원칙은 2단계와 같습니다 — 근거 없는 것은 그리지 않습니다.**
> 외래키가 명시된 자료면 사실로 그리고, 컬럼 이름으로 짐작해야 하는 관계는
> **기본으로 만들지 않습니다.** 만들더라도 `추정` 으로 표시하고 확인 목록에 올립니다.
> 그럴듯한 거짓 ERD 는 없는 것만 못합니다.

## 자주 막히는 곳

| 증상 | 원인과 조치 |
