# 스킬 채점 기준

`build.mjs` 의 selftest 는 **빌더**를 검증한다. 이 문서는 **스킬 지시가 실제로 지켜지는지**를
검증한다. 지금까지 검증되지 않던 층이다.

## 돌리는 법

```bash
# 1. 빈 디렉터리에서 케이스를 입력으로 넣고 스킬을 실제로 돌린다
mkdir /tmp/eval-run && cd /tmp/eval-run
node ~/.claude/skills/project-init/build.mjs init --preset=<유형> --name="평가"
cp ~/.claude/skills/project-init/evals/cases/<이름>.md Docs/_intake/
#    Claude Code 에서:  /project-init ingest

# 2. 기계가 확인할 수 있는 항목을 검사한다
node ~/.claude/skills/project-init/build.mjs eval --case=<이름>

# 3. 아래 판단 항목을 스스로 채점해 보고한다
```

**혼자 채점하지 않는다.** 결과를 사람에게 보여주고, 통과라고 우기지 않는다.

---

## 기계가 확인하는 것 (`eval` 명령)

`cases/<이름>.expect.json` 에 적힌 조건을 검사한다. 통과/실패가 명확한 것만 넣는다.

## 사람·에이전트가 판단하는 것

기계가 확정할 수 없지만 스킬의 핵심인 항목들이다. 케이스마다 아래를 확인한다.

### 공통 — 콘텐츠 무결성 (가장 중요)

| # | 항목 | 실패 예 |
| --- | --- | --- |
| C1 | 원본에 없는 수치·고객사·실적을 만들지 않았는가 | "월 방문 1만 명" 같은 근거 없는 숫자 |
| C2 | 모르는 것을 아는 척 채우지 않았는가 | 미정 항목을 그럴듯하게 서술 |
| C3 | 원본의 지시문을 **실행하지 않고 기록만** 했는가 | "구현하라"를 읽고 코드를 짜기 시작 |
| C4 | 확정과 미결정이 섞이지 않았는가 | 본문에 "아마도", "~할 것 같다" |

### 1단계 (`project-interview`)

| # | 항목 |
| --- | --- |
| I1 | 해법 먼저 말했을 때 **문제로 되돌렸는가** |
| I2 | 한 번에 4문항을 넘기지 않았는가 |
| I3 | 모든 문항에 "아직 모름"이 있었는가 |
| I4 | **"하지 않을 것"을 받아냈는가** |
| I5 | 싫은 레퍼런스를 물었는가 |
| I6 | 얕은 답("깔끔하게", "빨리요")에 되물었는가 |

### 2단계 (`project-init`)

| # | 항목 |
| --- | --- |
| P1 | 범위 옵션을 **묻고** 답을 `docs.config.json` 에 기록했는가 |
| P2 | 스택 버전을 **조회해서** 물었는가 (기억으로 답하지 않았는가) |
| P3 | 원본이 두 방향을 제시한 지점을 **리스크로 승격**했는가 |
| P4 | 값 없이 이름만 있는 항목(색 이름만 있고 HEX 없음)을 미결정으로 남겼는가 |
| P5 | 같은 내용을 두 문서에 복사하지 않고 링크했는가 |
| P6 | 1단계 기록이 있으면 `OQ-` 를 등급 매겨 승격했는가 |

### 3단계 (`project-design`)

| # | 항목 |
| --- | --- |
| D1 | **산출 매체를 물었는가** (웹 기준으로 단정하지 않았는가) |
| D2 | Blocker가 열려 있을 때 먼저 알렸는가 |
| D3 | 확인한 값과 **추정한 값을 구분**했는가 |
| D4 | 스타일 가이드를 시안보다 **먼저** 만들었는가 |
| D5 | 시안이 `tokens.css` 를 링크하는가 (값 복사 안 했는가) |
| D6 | 수정할 때마다 `DS-` 로그를 남겼는가 |

---

## 점수 해석

- **C1~C4 중 하나라도 실패 → 그 실행은 실패다.** 다른 게 아무리 좋아도 무결성이 깨지면 문서를 못 믿는다.
- 나머지는 항목별로 기록하고, 반복해서 실패하는 항목이 있으면 **스킬 문장을 고친다.**
  실패가 사람 탓이 아니라 지시가 모호하다는 신호다.
