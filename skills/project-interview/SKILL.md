# project-interview

**1단계 — 기획안 작성.** 머릿속의 문제·아이디어를 인터뷰로 끌어내 기획안 하나로 만든다.

산출물은 기획안 1개와 추적 기록 2개, 총 3개다.
그 다음은 `project-init` 스킬이 받아 문서 22종과 HTML로 펼친다.

```
[1] project-interview   아이디어 → 기획안        ← 이 스킬
[2] project-init        기획안 → 문서 + HTML
```

## 원칙

**1. 문제부터, 해법은 나중.**
사용자가 "○○를 만들어줘"로 시작하면 **한 번은 되돌린다.** 무엇을 만들지가 아니라
무엇이 문제인지를 먼저 확정한다. 해법을 먼저 고정하면 잘못된 것을 잘 만들게 된다.

**2. 모르면 모른다고 적는다.**
빈칸을 그럴듯하게 채우지 않는다. 미확정은 미확정으로 넘긴다 —
2단계가 그걸 Blocker로 승격시킨다. 지어낸 값은 그 기회를 없앤다.

**3. 선택지를 먼저 준다.**
"어떤 기능이 필요하세요?" 같은 백지 질문은 답하기 어렵다. 후보를 제시하고 고르게 한다.
모든 문항에 **"아직 모름"** 성격의 선택지를 둔다.

**4. 한 번에 최대 4문항.**
인터뷰가 심문이 되면 답변 품질이 떨어진다. 묶음으로 나눠 묻고, 답을 확인하며 진행한다.

**5. 답에 따라 다음 질문을 바꾼다.**
사내 시스템이면 검색 노출을 묻지 않는다. B2C면 개인정보를 더 묻는다.
이미 말한 것을 다시 묻지 않는다.

**6. 얕은 답은 되묻는다.** 아래 표 참조.

## 되물어야 하는 신호

| 이렇게 말하면 | 이렇게 되묻는다 |
| --- | --- |
| "앱으로 만들고 싶어요" | 왜 앱이어야 하는지. 웹으로 안 되는 이유가 있는지 |
| "AI를 넣고 싶어요" | 어떤 작업을 대체·보조하는지. 규칙으로 처리되는 일은 아닌지 |
| "일단 다 되게" | 없으면 출시 못 하는 것 3가지만 |
| "경쟁사처럼" | 그 서비스의 **어느 부분**이 좋은지 |
| "빨리요" | 마감 날짜와, 그 날짜여야 하는 이유 |
| "예산은 나중에" | 범위 상한만이라도. 범위는 예산에 종속된다 |
| 목표가 측정 불가 | 숫자로, 안 되면 관찰 가능한 상태로 |
| "하지 않을 것"이 비어 있음 | 후보를 제시해서라도 받아낸다 |

되묻는 것은 반대하는 게 아니다. 사용자가 이미 정했다고 하면 그 결정을 존중하고,
**근거를 기획안에 적는다.**

## 진행

1. **먼저 사용자가 이미 말한 것을 정리해 보여준다.** "지금까지 이해한 것" 3~5줄.
   틀린 부분을 먼저 잡는 것이 질문보다 빠르다.
2. `INTERVIEW.md`의 단계(A~I)를 참고해 **묶음으로** 묻는다. 전부 묻지 않는다.
   - 최소 필수: **A 정체 · B 문제 · D 성공 · E 범위 · E-2 규모**
   - 나머지는 프로젝트 성격에 따라
   - **E-2 규모는 건너뛰지 않는다.** 이 답이 2단계 문서 세트의 크기를 정한다.
     안 물으면 2주짜리 랜딩과 7개월짜리 커머스가 똑같은 문서 33개를 받는다.
3. 답을 받을 때마다 **모순이나 공백을 지적한다.**
   "목표는 신규 고객 확보인데 대상이 기존 직원으로 되어 있습니다" 같은 것.
4. 인터뷰가 끝나면 `templates/brief.md` 형식으로 기획안을 쓴다.
5. `Docs/_intake/` 가 없으면 만들고 거기에 저장한다.
6. `node validate.mjs <기획안> <결정기록> <미결기록>`으로 전달 계약을 검증한다. 스킬 회귀 점검에는 `fixtures/`의 익명 샘플 3개를 사용한다.
7. 사용자에게 **요약 + 미확정 목록**을 보여주고 다음 단계를 안내한다.

## 산출물 — 파일 3개

| 파일 | 내용 |
| --- | --- |
| `Docs/_intake/YYYY-MM-DD-<slug>.md` | **기획안** (`templates/brief.md`). 2단계 흡수 대기열 |
| `Docs/_discovery/decisions.md` | **인터뷰 결정 기록** (`templates/decisions.md`) |
| `Docs/_discovery/open-questions.md` | **인터뷰 미결 사항** (`templates/open-questions.md`) |

기획안 프론트매터에 2단계가 쓸 힌트를 담는다 — `profile`, `suggested_preset`, `option_hints`.
그래야 2단계에서 같은 질문을 반복하지 않는다.

기획안 **§7 산출물 범위**는 2단계의 **산출물 정의서 v1** 이 된다.
2단계는 그 표에서 WBS 과업을 뽑으므로, 여기가 비면 과업 근거가 사라진다.
`필요` 와 `고객 공유` 두 칸을 특히 정확히 받는다 — 후자가 ELI5 적용 범위를 정한다.
모르는 행은 대신 정하지 말고 `TODO(client)` 로 남긴다.

`profile` 은 **문서 세트의 크기를 정하는 축**이다. `suggested_preset` 이 *어떤 종류*를
고른다면 `profile` 은 *얼마만큼*을 고른다. 둘 다 있어야 프로젝트에 맞는 분량이 나온다.

| 축 | 값 | 정하는 것 |
| --- | --- | --- |
| `scale` | `solo` `small` `standard` `large` | 공수·인력 규모. 문서 수에 가장 크게 작용한다 |
| `risk` | `low` `standard` `regulated` | 돈·개인정보·법규 취급 여부. 보안·권한 문서를 켠다 |
| `delivery` | `prototype` `mvp` `production` | 완성도 목표. 출시 관련 문서를 켠다 |

**모르면 넓은 쪽으로 둔다** — `large` / `regulated` / `production`.
작게 잡아 문서를 잃는 것보다 크게 잡아 지우는 편이 낫다.

2단계가 흡수를 마치면 기획안도 `Docs/_discovery/`로 옮겨진다.
결국 **1단계 기록 3종이 한 폴더에 모이고**, HTML에서 `1단계 · 기획` 메뉴로 따로 보인다.

### 기록 규칙 — 2단계와 섞지 않는다

| | 1단계 (이 스킬) | 2단계 (project-init) |
| --- | --- | --- |
| 결정 | `DI-001` — 사람이 말로 정한 것 | `D-001` — 문서·기술을 만들며 정한 것 |
| 미결 | `OQ-01` — 묻고 답을 못 받은 것 | `B-01` `H-01` `M-01` — 등급이 매겨진 리스크 |
| 메뉴 | `1단계 · 기획` | 단계별 문서 그룹 |

**인터뷰 도중에 바로 기록한다.** 끝나고 몰아서 쓰면 근거가 사라진다.

- 사용자가 **명시적으로 정한 것** → `decisions.md`에 질문·답변·근거까지
- 사용자가 **"모르겠다 / 나중에 / 확인해봐야 안다"** → `open-questions.md`
  대신 정하지 않는다. 추정으로 채우면 2단계가 리스크로 인식할 기회를 잃는다.

### 로그 작성자 규칙

- 모든 `DI-`·`OQ-` 기록에 `일자`, `AI`, `계정`을 남긴다.
- 일자는 로컬 시간 `YYYY-MM-DD HH:mm` 형식이다.
- AI는 실제 작업 도구명(`Claude Code`, `Codex`, `Cursor` 등), 계정은 해당 도구의 사용자명 또는 작업자명이다.
- 계정을 알 수 없으면 한 번만 묻고, 답이 없으면 `미확인`으로 기록한다. 추정하지 않는다.
- 날짜별 `## YYYY-MM-DD` 아래에 항목을 두어 2단계 HTML에서 날짜 토글로 렌더되게 한다.
- 같은 질문 묶음에서 나온 결정은 주제별로 합쳐 기록한다. 단순 자산 사실과 의사결정을 분리한다.

### 2단계 전달 계약

- `profile` 의 세 축을 모두 채운다. 값은 위 표의 것만 쓴다.
- `option_hints`는 2단계 옵션 13개를 모두 포함한다. 값은 `true`, `false`, `unknown`만 쓴다.
- 전체 목표 범위와 첫 출시 범위를 분리한다.
- 비용은 초기비, 월 고정비, 사용량 비용, 운영 시간 부담으로 나눈다.
- 기술 스택은 확정하지 않고 원본이 강제한 제약만 `stack_hints`에 전달한다.

끝낼 때 이렇게 안내한다:

```
기획안을 만들었습니다.
  Docs/_intake/2026-08-13-프로젝트명.md   기획안
  Docs/_discovery/decisions.md            결정 N건
  Docs/_discovery/open-questions.md       미결 N건

미결 중 프로젝트를 막을 만한 것:
  · OQ-02 …

다음: /project-init ingest
```

## 하지 말 것

- **인터뷰 없이 기획안을 쓰기.** 한 문장만 듣고 그럴듯한 10페이지를 만들면 전부 추측이다.
  최소 A·B·D·E는 묻는다.
- 확인되지 않은 수치·경쟁사 정보·시장 규모를 채워 넣기.
- 사용자가 "모르겠다"고 한 것을 대신 정하기. 그대로 미확정으로 남긴다.
- 기술 스택을 여기서 확정하기. 스택은 4단계이고, 2단계에서 버전까지 따로 묻는다.
- 한 번에 20개 질문 던지기.
